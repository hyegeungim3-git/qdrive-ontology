# Qdrive Ontology — 대구 시내버스 데이터의 의미 구조

운행 데이터가 **무엇을 뜻하고 무엇을 움직이나**를 다루는 독립 도구.
운영 플랫폼([qdrive-unified](https://github.com/hyegeungim3-git/qdrive-unified))이 "데이터가 어떻게 들어와 어떤 화면이 되나"를 다룬다면, 여기는 그 아래에 깔린 **문법**을 다룬다.

- **라이브**: https://hyegeungim3-git.github.io/qdrive-ontology/
- **운영 플랫폼**: https://hyegeungim3-git.github.io/qdrive-unified/

## 핵심 사슬

```
관측(Evidence) ─뒷받침한다→ 판정(Claim) ─반영된다→ 성과(Outcome) ←올린다─ 조치(Lever)
```

무슨 일이 있었고(관측), 그게 무슨 뜻이며(판정), 결과가 어떻게 되었고(성과), 우리가 무엇을 당겼는가(조치).
어떤 숫자든 이 사슬을 거꾸로 되짚어 근거를 댈 수 있어야 한다는 것이 이 도구의 전제다.

## 13단계 — 정의 · 활용 · 운영 · 개정

**정의** — 무엇이 무엇과 어떻게 연결되나
| 단계 | 무엇을 |
|---|---|
| ① 스페이스 | 9개(규정·자산·주체·관측·개념·판정·집단·성과·조치) × 노드 타입 35종 |
| ② 관계 문법 | 스페이스 쌍마다 허용된 관계 어휘 30종 + 어휘 사전 |
| ③ 표준 정렬 | **국제 표준 10종**에 우리 어휘를 대응 — 정렬 강도는 SKOS 매핑 관계 그대로 |
| ④ 문법 검증 | 관계를 조합해 보고 허용/거부 확인 — **허용률 1.4%** |

**활용** — 그래서 무엇에 쓰나
| 단계 | 무엇을 |
|---|---|
| ⑤ 근거 사슬 | 성과 지표 **6종 전체** 역추적. 지표마다 근거의 성격이 다르다 — 실측·환산·미측정 |
| ⑥ 조치 시뮬레이션 | 조치를 당기면 성과가 얼마나 움직이나. 근거 유형별 신뢰도 상한 |
| ⑦ 영향 분석 | 스페이스 × 변경 유형 → I1~I7 + 전파 범위 + 흔들리는 화면 |

**운영** — 어떻게 관리하고 넘기나
| 단계 | 무엇을 |
|---|---|
| ⑧ 액티브 메타데이터 | 4계층 12속성 — 계보·의존성은 문법에서, **행동 계층은 격리 이력에서 실시간 갱신** |
| ⑨ SHACL 실검증 | 지금 이 데이터를 **실제 SHACL 엔진에 넣어 돌린다** — 결함을 주입하면 정말로 막힌다 |
| ⑩ 격리 큐 | 막힌 레코드가 **실제로 보류되는 곳** — 재처리·예외 승인·원천 수정 요청 + **규칙 역제안** |

**개정** — 고치고 내보낸다
| 단계 | 무엇을 |
|---|---|
| ⑪ 문법 발행 | 개정안을 승인하면 **문법이 실제로 바뀐다** — 버전 라벨만 올라가는 것이 아니다 |
| ⑫ 문법 비교 | 개정 전후를 **나란히** — 발행 전 미리보기도 같은 계산 |
| ⑬ 내보내기 | 7형식 — **JSON-LD · Turtle(OWL) · Cypher · SHACL · 문법 명세서 · 격리 이력 · 개정 이력** |

## 표준 위에 서 있다

자체 문법만으로는 우리끼리만 아는 구조가 된다. 그래서 어휘마다 국제 표준 대응을 붙였다.

| 표준 | 기관 | 우리에게 왜 |
|---|---|---|
| **PROV-O** | W3C | 관측 → 판정 → 성과가 바로 PROV의 파생 사슬 |
| **SOSA/SSN** | W3C·OGC | DTG·OBD·RTK가 만드는 것이 정확히 `sosa:Observation` |
| **Transmodel/NeTEx · GTFS** | CEN · 사실상 표준 | 노선·정류장·회차는 이미 표준이 있다 |
| **DQV** | W3C | 품질 6룰 = `dqv:Metric`, 통과율 = `dqv:QualityMeasurement` |
| **SKOS** | W3C | 위험운전 8종 같은 분류 어휘 · 정렬 강도 표기 자체 |
| **ODRL** | W3C | 규정을 사람 말이 아니라 기계가 읽는 정책으로 |
| **OWL-Time · GeoSPARQL · SHACL** | W3C · OGC | 시간 구간 · 공간 대조 · 제약 검증 |
| **공단 DTG 409/521** | 한국교통안전공단 | 국내 법정 — 이걸 지키는 것이 먼저 |

정렬 강도를 억지로 «정확 일치»로 올리지 않는다. 조치→성과의 인과 어휘(올린다·낮춘다)는 대응 표준이 없어 **고유**로 둔다.

## SHACL — 실제로 막는 규칙

OWL은 어휘를 정의할 뿐 검사하지 않는다. 막는 것은 SHACL이다. 4종을 생성한다.

1. **속성 제약** — 필수·자료형·값 범위·열거값 (속도 0~120km/h, 위험운전 8종만, 위도 33~39)
2. **관계 제약** — 도착 클래스·카디널리티·필수 관계
3. **문법 제약** — `sh:closed`로 문법에 없는 관계 차단
4. **도메인 규칙** — 업무 원칙을 제약으로
   - 근거 관측이 없는 판정은 만들 수 없다
   - 감점 확정에는 담당자(`decidedBy`)가 반드시 있어야 한다 (자동 확정 금지)
   - 분석셋에 실명을 둘 수 없다 (가명키만)
   - 회차 연료가 주행거리 대비 1.0 m³/km를 넘으면 누적값 오기록 (`sh:sparql`)

## 실제로 돌린다 — ⑨ SHACL 실검증

제약을 **생성**하는 것과 **돌리는** 것은 다르다. ⑨단계는 시뮬레이터가 지금 내보내는 값을
RDF 데이터 그래프로 옮겨, W3C SHACL 구현체(`rdf-validate-shacl`)에 그대로 넣는다.

- **데이터 그래프** — 인스턴스마다 노드 타입(`qd:RiskEvent`)과 스페이스(`qd:Evidence`) 양쪽으로
  타입을 붙인다. 속성 셰이프는 노드 타입을, 관계·닫힘 셰이프는 스페이스를 target하기 때문.
  관계 술어는 손으로 적지 않고 문법(`REL_META`)에서 꺼내 쓴다.
- **결함 주입 8종** — 버튼 하나로 일부러 규칙을 깬다. 각각 서로 다른 제약에 걸리도록 설계돼 있다.

| 결함 | 걸리는 제약 |
|---|---|
| 표준 밖 이벤트 코드 | `sh:in` |
| 속도 범위 초과 | `sh:maxInclusive` |
| 필수 분류 누락 | `sh:minCount` |
| 문법 밖 관계 | `sh:closed` |
| 근거 없는 판정 | `sh:minCount` · 역경로 |
| 감점 자동 확정 | `sh:minCount` |
| 기사 실명 노출 | `sh:maxCount 0` **+** `sh:closed` (두 규칙이 겹쳐 막는다) |
| 회차 연료 누적값 | `sh:sparql` (보조 검사) |

**엔진이 못 하는 것도 적어 둔다** — 브라우저 검증기는 `sh:sparql` 기반 제약을 지원하지 않는다.
그래서 「회차 연료」 규칙만 같은 조건을 JS로 따로 돌리고 결과에 «보조 검사»로 표시한다.
내보내기 파일에는 원래대로 `sh:sparql`로 들어가고, 서버측 검증기(pySHACL·TopBraid)는 이것도 돈다.

## 막고 끝내지 않는다 — ⑩ 품질 격리 큐

검증은 «막았다»로 끝나지 않는다. 막힌 레코드를 **누가 어떻게 푸는지**까지가 데이터 관리다.
⑨에서 걸린 레코드는 자동으로 큐에 적재된다(같은 레코드·같은 제약은 중복 적재하지 않는다).

**격리는 삭제가 아니다.** 원본은 그대로 두고 하류(정제 저장소·분석셋)로만 내려보내지 않는다.

| 조치 | 언제 |
|---|---|
| **재처리** | 원인이 해소돼 다시 적재 — 단말 시각 보정·통신 복구 |
| **예외 승인** | 규칙은 맞지만 이 건은 정당하다고 담당자가 판단 — **사유 필수** |
| **원천 수정 요청** | 원천 시스템이 잘못 보내고 있다 — 커넥터 담당에게 |

**어떤 위반은 예외 승인으로 풀 수 없다.** 「불이익 결정 자동화 금지」·「가명 처리」는 규정 스페이스에
못 박혀 있다. 큐에서 클릭 한 번으로 우회할 수 있으면 그 규정은 장식이 된다 — 그래서 버튼을 아예 잠근다.

### 온톨로지가 있어서 할 수 있는 것 — 하류 영향 계산

격리 화면은 «이 레코드를 보류하면 **어떤 성과가 흔들리는지**»를 함께 보여준다.
`관측 ─뒷받침한다→ 판정 ─반영된다→ 성과` 경로를 그래프에서 실제로 걸어 계산한 결과다.

- 회차 기록이 막히면 → **연료 절감률**
- 위험운전 패킷·정당 판정이 막히면 → **해당 차량 안전점수**
- 기사 노드(실명 노출)가 막히면 → **없음.** 성과까지 닿는 경로가 없다 — 보류해도 지표는 흔들리지 않는다.
  «막으면 손해»라는 반론이 성립하지 않는 경우를 숫자가 아니라 **경로로** 답한다.

### 운영 플랫폼과의 관계

운영 플랫폼(데이터 관리자)의 격리 큐는 룰별 **건수**를 다룬다(6개 룰 · 재처리 이력).
여기는 SHACL이 위반 노드를 정확히 지목하므로 **레코드 단위**로 다루고, 하류 영향을 관계로 계산한다.
둘은 같은 원칙 위에 있다 — 버리지 않고, 원인을 고치면 재처리되며, 그 이력이 곧 관리의 근거가 된다.

## 고리를 닫는다 — 규칙 역제안 · 라이브 메타데이터

여기까지 오면 한 방향으로만 흐르던 것이 순환이 된다.

### 규칙 역제안 — 큐가 문법에게 말을 건다

같은 규칙이 계속 **예외 승인**으로 풀린다면, 틀린 것은 데이터가 아니라 규칙일 수 있다.
**처리 방식의 분포가 곧 진단**이다.

| 무엇이 많은가 | 진단 | 뜻 |
|---|---|---|
| 예외 승인 | **규칙 재검토** | 규칙이 현실과 안 맞는다 — 규칙을 고쳐라 |
| 재처리 | **원천 점검** | 규칙은 옳다. 원천이 일시적으로 흔들렸다 — 단말·통신을 봐라 |
| 원천 수정 요청 | **커넥터 점검** | 원천이 계속 규격을 어긴다 — 커넥터를 고쳐라 |

제안은 제약 종류에 따라 다르다. 범위 제약이면 «임계값 재산정», 열거면 «코드 목록보다 원천 매핑을 먼저»,
필수 지정이면 «정말 모든 레코드에 있어야 하는지», 닫힘이면 «관계 어휘에 추가할지 원천에서 뺄지».
담당자가 실제로 적은 사유도 같이 붙는다 — 진단의 근거가 통계가 아니라 사람의 말이어야 하기 때문이다.

**완화하면 안 되는 규칙은 제외한다.** 「불이익 결정 자동화 금지」·「가명 처리」처럼 규정에서 온 규칙은
예외가 쌓여도 «규칙 재검토»로 올리지 않는다. 예외가 많다는 건 그 규칙이 틀렸다는 뜻이 아니라
**현실을 고쳐야 한다는 뜻**이다. 그렇지 않으면 이 화면 자체가 규정을 무력화하는 통로가 된다.

### 라이브 메타데이터 — 「액티브」라고 이름 붙였으면 움직여야 한다

계보·의존성은 **문법**에서 나온다. 사용량·파급의 라이브 부분은 **실제로 있었던 일**에서 나온다 —
레코드가 격리됐다는 것은 그것이 하류로 안 내려갔다는 뜻이고, 그 자체가 사용량의 사실이다.

- 사용량 `+ 격리로 하류 전달이 막힌 레코드 N건 (보류 M · 처리 K)`
- 파급 `+ 보류로 지금 흔들리는 성과: 연료 절감률 · …`

⑧ 화면의 행동 계층에 «라이브» 표시가 붙고, 격리 큐를 처리하면 **그 자리에서 값이 바뀐다.**

### 「고치자」와 「고치면 이만큼 흔들린다」를 같은 자리에

역제안이 «규칙 재검토»를 내면, 바로 아래에서 **그 규칙을 고치면 무엇이 흔들리는지**를 편다.
규칙 완화 제안을 ⑦ 영향 분석이 이해하는 «스페이스 × 변경 유형»으로 환산해 **같은 전파 엔진**에 넣는다 —
여기서만 쓰는 별도 계산을 만들면 두 화면의 답이 갈라진다.

| 걸린 제약 | 환산되는 문법 변경 |
|---|---|
| `sh:in` | 개념 스페이스에 코드값 추가 (신규 추가) |
| `sh:maxInclusive` · `sh:sparql` | 값 범위·임계값 조정 (값 수정) |
| `sh:minCount` | 필수 지정 해제 (관계 제거) |
| `sh:closed` | 관계 어휘에 추가 — 문법 확장 (관계 추가) |

두 개의 문이 열린다.
- **⑦ 영향 분석에서 자세히** — 그 조합이 선택된 채로 열린다
- **④ 문법 검증에서 이 조합 눌러보기** — 문법 밖 술어가 반복될 때, 그 조합이 정말 막히는지 바로 확인

### 감사 제출용 격리 이력 (⑪)

다른 형식은 전부 **문법**을 낸다. 이것만 **실제로 있었던 일**을 낸다.
감사에서 묻는 것은 셋이고, 그 순서대로 답한다.

1. **요약** — 격리 총계 · 보류 · 재처리 · 예외 승인 · 원천 수정 요청
2. **규정 보호 규칙의 우회 여부** — 해당 규칙으로 격리된 건수와 그중 예외 승인으로 우회된 건수.
   시스템이 막고 있으므로 정상이라면 **0건**이고, 그 사실 자체가 증거가 된다
3. **격리 레코드 전체** — 시각·레코드·스페이스·규칙·심각도·처리·담당자·사유·하류 영향
4. **규칙별 진단** + 5. 처리 원칙

큐가 비어 있으면 «격리 0건은 검사를 안 했다는 뜻일 수도 있다»고 함께 적는다 —
0을 성적표로 읽지 않게 하는 것도 이력의 몫이다.

## 고리가 닫힌다 — ⑪ 문법 발행

제안에서 멈추면 온톨로지는 여전히 손으로 고치는 문서다. 발행이 버전 라벨만 바꾸는 것도 마찬가지 —
그건 연극이다. **그래서 발행하면 문법 정의 자체를 갈아끼운다.**

```
문법 → 검증 → 격리 → 역제안 → 개정안 → 발행 → 문법
```

### 발행하면 실제로 무엇이 바뀌나 (실측)

| 확인 지점 | v1.0 | v1.1 발행 후 |
|---|---|---|
| ④ 문법 검증 — 관측→성과 «반영된다» | ❌ NO_DIRECTION | **✅ 허용** |
| 허용 조합 | 30 (11개 방향) | **31 (12개 방향)** |
| ⑨ SHACL 실검증 — 같은 결함을 켠 채로 | ✗ 위반 2건 | **✅ conforms** |
| 셰이프 그래프 | 813 트리플 | **821 트리플** |
| ⑫ 내보내기 | `qdrive-ontology-v1.0` | **`qdrive-ontology-v1.1`** + 새 관계 포함 |

**되돌리기도 대칭이다.** v1.0으로 되돌리면 방향 12→11, 셰이프 821→813, 같은 결함이 다시 잡힌다.

### 개정 6종

역제안의 제약 종류마다 실제로 손대는 자리가 다르다.

| 제약 | 개정 | 손대는 곳 |
|---|---|---|
| `sh:closed` | 관계 어휘에 추가 | 메타 엣지 |
| `sh:minCount` (관계) | 필수 지정 해제 | 관계 메타 |
| `sh:minCount` (역경로) | 도메인 규칙 해제 | **민감 — 핵심 사슬 완화** |
| `sh:in` | 열거값 추가 | 노드 타입 속성 |
| `sh:maxInclusive` | 값 범위 조정 | 노드 타입 속성 |
| `sh:sparql` | 임계값 재산정 | 도메인 규칙 상수 |

### 발행에 건 세 가지 잠금

1. **규정에서 온 규칙은 개정안에 담기지 않는다** — 「불이익 결정 자동화 금지」·「가명 처리」는
   `toAmendment`가 아예 `null`을 낸다. 버튼이 뜨지 않는다.
2. **핵심 사슬을 느슨하게 하는 개정은 확인란 없이 발행되지 않는다** — 「근거 없는 판정 금지」 해제처럼
   사슬을 무르게 하는 항목은 «그 위험을 알고 승인합니다»를 체크해야 발행 버튼이 열린다.
3. **이미 격리된 레코드는 자동으로 풀리지 않는다** — 새 문법은 앞으로 들어오는 데이터에 적용된다.
   규칙이 바뀌었다고 지난 판정이 조용히 뒤집히면 그게 더 위험하다.

### 개정의 근거가 이력에 남는다

「누가 언제 승인했나」만이 아니라 **「무슨 데이터가 이 개정을 요구했나」** 까지 남는다 —
격리 몇 건이 예외 승인으로 풀렸고 담당자가 뭐라고 적었는지가 그대로 개정 사유가 된다.
문법이 누군가의 취향으로 바뀌지 않았다는 증거다.

## 무엇이 달라졌나 — ⑫ 문법 비교

«v1.1로 올렸다»는 말만으로는 무엇이 달라졌는지 알 수 없다. 문법은 규격이라
**무엇이 늘었는지만큼 무엇이 그대로인지**도 중요하다. 그래서 바뀐 항목만 세지 않고 안 바뀐 축도 함께 낸다.

| 축 | v1.0 | → | v1.1 | |
|---|---|---|---|---|
| 관계 방향 | 11개 | → | **12개** | 바뀜 |
| 관계 어휘 | 30종 | → | 30종 | 그대로 |
| 허용 조합 | 30 | → | **31** | 바뀜 |
| 필수 관계 | 2종 | → | 2종 | 그대로 |
| 도메인 규칙 | 4종 | → | **3종** | 바뀜 |
| 회차 연비 상한 | 1.0 | → | 1.0 | 그대로 |

변경 항목은 영역별로 잡아낸다 — 관계 방향 · 관계 어휘 · 필수 지정 · 카디널리티 · 열거값 · 값 범위 ·
도메인 규칙 · 임계값. 그리고 **관계 문법 전체를 방향별로 좌우에 놓아**, 추가된 어휘는 초록 `＋`,
사라진 어휘는 취소선으로 보인다.

### 발행 전에도 같은 계산으로 본다

승인 전에 결과를 볼 수 없는 승인 화면은 승인이 아니라 **서명**이다.
그래서 비교 대상에 «현재 + 개정안 N건»을 넣었다. 아직 발행하지 않은 개정안을 반영하면 어떻게 되는지
발행에 쓰는 것과 **똑같은 함수(`derive`)** 로 계산한다 — 미리보기 전용 계산을 따로 만들면
«미리보기와 실제가 다르다»가 생긴다.

구조도 그에 맞게 갈랐다.

```
derive(스냅샷, 개정안) → 새 스냅샷    부작용 없음 · 미리보기와 발행이 같은 함수
commit(스냅샷)                        여기서만 살아 있는 정의를 갈아끼운다
```

## 규격만 넘기면 절반이다 — 개정 이력 내보내기

다른 도시·사업자에게 문법 파일만 넘기면 «지금 이 규격»은 전달된다. 하지만 받아 쓰는 쪽이 정말 알고
싶은 것은 **왜 이렇게 됐나**다 — 어떤 조항이 나중에 열렸고, 무엇이 그것을 요구했는지.
그게 없으면 다음 개정 때 같은 논쟁을 처음부터 다시 한다.

`qdrive-개정이력.md` 는 버전마다 셋을 낸다.

1. **요약** — 6축의 이전/이후와 «바뀜/그대로»
2. **무엇이 바뀌었나** — 영역별 변경표
3. **왜 바꿨나** — 근거 규칙 · 예외 승인 건수 · **담당자가 적은 사유 원문** · 영향 좌표

문서 맨 앞에는 개정 원칙 4개를 박아 둔다 — 개정은 데이터가 요구할 때만 / 규정에서 온 규칙은 완화
대상이 아니다 / 핵심 사슬 완화는 별도 승인 / **발행은 소급하지 않는다**.

개정이 없으면 «최초 정의 v1.0 그대로»라고 적고, **«개정 0회가 나쁜 신호는 아니지만 검증을 실제로
돌리고 있는지는 격리 이력으로 함께 확인해야 한다»** 고 덧붙인다. 0을 성적표로 읽지 않게 하는 것이
이력의 몫인 것은 격리 이력과 같다.

**JSON-LD도 개정 계보를 들고 다닌다** — `version`, `@id`가 현재 버전을 가리키고 `revisions` 배열에
버전별 개정 항목·근거 규칙·예외 승인 건수가 들어간다. 기계가 읽는 파일도 자기가 몇 번째 개정인지 안다.

## 수치는 살아 있다

내장 시뮬레이터 엔진(버스 9대 · 3노선)이 돌면서 관측·판정·성과·조치 인스턴스를 실제로 만들어낸다.
헤더의 **배속(1×~60×)** 을 올리면 숫자가 늘어나고, **시연 버튼**(급감속·고장·민원·배차)을 누르면 해당 스페이스의 인스턴스가 즉시 생긴다.

## 실행

```bash
npm install
npm run dev     # http://localhost:5173/qdrive-ontology/
npm run build
```

## 구조

```
src/
  sim/        ← 시뮬레이터 엔진 (qdrive-unified와 동일 코어 — 실단말 연동 시 PacketSource 교체)
  ontology/   ← meta.ts(스페이스·문법·조치) · impactmeta.ts(영향·메타데이터) + 화면 5종
  components/ ← 공용 UI · 데모 컨트롤
```

## 설계 노트

- **스페이스 이름은 우리 도메인 용어**로 정의했다. 지식그래프 일반 어휘(subject/resource/evidence…)를 그대로 쓰지 않은 것은, 최종 독자가 발주처 담당자이기 때문이다.
- **모르는 것을 아는 척하지 않는다** — 시뮬레이터 계수마다 근거 유형(실측/환산/추정/정성)을 붙이고, 근거가 약하면 신뢰도 상한 자체를 낮춘다.
- **불이익 결정은 자동화하지 않는다** — 판정 스페이스의 성숙도에 명시. 평가·징계·정산 확정은 사람이 한다.
- SVG 그래프는 `엣지 → 라벨 → 노드` 순서로 그린다. 노드마다 선과 도형을 함께 그리면 뒤 노드의 선이 앞 노드를 덮는다.
